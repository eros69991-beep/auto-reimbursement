# 自动报销助手 MVP 设计规格

日期：2026-09-03  
状态：待用户最终评审  
目标平台：本地网页（联网调用多模态 AI API）

## 1. 产品目标

把当前人工报销流程：

微信收到购买凭证图片 → 手工保存 → 手工找“总实付金额” → 手工归类 → 手写费用报销单 → 手工拼接凭证 → 月底交财务

改造成：

批量拖入图片 → 系统自动识别实付金额与分类 → 异常项进入待处理 → 用户手动决定何时结批 → 系统自动拆分并生成接近纸质模板 1:1 的电子报销单 → 按金额顺序自动排版原始凭证 → 导出一个完整 PDF 发给财务。

第一版核心指标：尽量让用户只处理异常图片，不逐张确认正常识别结果。

---

## 2. 第一版明确不做

- 微信自动收图
- 多用户登录/权限
- 审批流
- 银行接口
- 财务软件接口
- 云端账户
- 手机 App
- 自动退款追踪
- 真正的大模型微调 / Fine-tuning
- 复杂多人协作

---

## 3. 固定报销分类

系统分类只能从以下 10 类中选择，不允许 AI 自创分类：

1. 食材
2. 百慕达食材
3. 日常用品
4. 耗材
5. 能耗费
6. 人工费用
7. 肉类
8. 租金及管理费
9. 酒水
10. 员工餐

规则：一张凭证只归一个分类。公司后续可要求采购严格按分类拆单。

---

## 4. 核心工作流

### 4.1 上传

- 本地网页支持批量拖拽上传。
- 单次最多 50 张。
- 当月总量不限，可分批上传。
- 保持用户上传顺序，不按日期自动重排。
- 后台采用 3–5 张并发队列调用 AI。
- 失败自动重试。
- 最终失败或低置信度记录进入“待处理”。

### 4.2 自动识别

每张图片提取：

- 最终实付金额（核心）
- 分类（核心）
- 商家/来源（辅助）
- 交易日期（辅助）
- 置信度

图片来源不限定，可能包括微信/支付宝付款截图、淘宝/京东订单、外卖平台、转账截图、拍摄的小票及其他未知格式。

### 4.3 自动放行

建议默认阈值：

- 金额置信度 ≥ 0.95
- 分类置信度 ≥ 0.90

满足时直接进入“可报销”。

中等置信度：
- 结合历史学习规则再次判断。
- 二次判断一致则自动放行。
- 仍冲突则进入待处理。

低置信度或存在无法判断的多个支付金额：
- 禁止猜测。
- 进入待处理。

### 4.4 实付金额规则

AI 应优先理解：

实付 / 实付款 / 实际支付 / 已支付 / 支付金额 / 本次支付 / 合计支付

不得把以下金额直接视为最终报销金额：

原价 / 优惠 / 立减 / 余额 / 应付 / 单独运费 / 退款金额

若截图中存在多个可能的“最终支付金额”且无法可靠区分，则进入待处理。

---

## 5. 重复凭证检测

重复检测发生在调用 AI 前，以降低误报和 API 成本。

### 5.1 完全重复
- 为图片生成内容指纹。
- 同一图片即使改文件名，也应能识别。
- 默认阻止重复入账。

### 5.2 疑似重复
结合图片相似度、金额、商家、日期和历史记录判断。

若高度相似：
- 进入待处理。
- 显示历史凭证。
- 用户可“确认不是重复，继续加入”。

检测范围：整个历史数据库，包括已归档月份。

---

## 6. AI 学习系统

第一版不训练新模型，而采用：

多模态 AI + 本地历史纠正 + 供应商/关键词规则

用户若把某供应商从“日常用品”修正为“耗材”，系统记录：
- 商家/特征
- AI 原分类
- 用户最终分类
- 用户确认次数

以后再次出现相似凭证时，优先参考历史规则。

建议：
- 连续确认 3 次后，可升级为强规则。
- 单独提供“AI学习记录”页面。
- 支持查看、编辑、删除规则。
- 学习记录与具体 AI 服务商解耦。

## 7. 报销池

每一笔记录显示：
- 凭证缩略图
- 最终实付金额
- 分类
- 状态
- 商家/日期（辅助）

支持：
- 修改金额
- 修改分类
- 查看原图
- 标记退款
- 删除
- 查看识别结果

顶部展示：
- 当前可报销笔数
- 总金额
- 10 类分类小计

---

## 8. 报销批次

不存在固定金额门槛。

由用户手动点击“生成报销单”结批。

系统对本次选中的“可报销”记录进行自动拆单和排版。

---

## 9. 自动拆单与排版

原则：

1. AI 不参与排版。
2. 排版由确定性程序规则完成。
3. 同分类的凭证保持原上传顺序。
4. 一个分类尽量完整出现在同一张报销单。
5. 系统根据摘要实际占用空间决定同一张单可组合多少分类。
6. 尽量填满版面，但不能挤坏模板。
7. 极少数单分类超出整页容量时，可提示人工处理；第一版不为极端场景做复杂算法。

### 9.1 报销单填写方式

每个分类占一个“报销项目”区域。

“摘要”只写该分类下每张图片的总实付金额，例如：

耗材  
摘要：36.33  17.30  35.75  41.36  
金额：130.74

不自动填写商品明细名称。

---

## 10. 费用报销单电子模板

目标：尽量接近现有纸质《费用报销单》1:1 复刻。

保留并自动填充/保留空白：
- 费用报销单标题
- 报销部门（可编辑）
- 年 / 月 / 日（可选）
- 报销项目
- 摘要
- 金额
- 合计
- 人民币大写金额
- 附件张数
- 右侧备注区
- 报销人
- 会计主管（空白）
- 复核（空白）
- 出纳（空白）
- 领导审批（空白）

金额统一保留 2 位小数。

所有金额计算、分类小计、整单合计、中文大写金额由程序完成，不由 AI 计算。

---

## 11. 报销人

只有“报销人”需要系统填写。

支持两种模式：
1. 普通文字姓名
2. 上传手写签名图片

两种模式都可在设置中切换。

---

## 12. 备注信息库

支持维护多个备注模板。

每条备注包含：
- 备注名称
- 自由多行内容

支持新增、编辑、删除。

生成每张报销单时从下拉框中选择对应备注，自动填入右侧“备注”区域。

---

## 13. 凭证附件排版

附件顺序必须和报销单摘要金额顺序严格一致。

示例：

报销单摘要：
164.88 → 305.91 → 41.00 → 171.96

附件：
1. 耗材 · ¥164.88 · 原始凭证
2. 耗材 · ¥305.91 · 原始凭证
3. 耗材 · ¥41.00 · 原始凭证
4. 耗材 · ¥171.96 · 原始凭证

原则：
- 不按日期重排。
- 原图不修改。
- 每张图可添加小型文字标记，但不能覆盖重要凭证内容。

---

## 14. 退款处理

退款不是主状态，而是报销记录属性。

### 全额退款
- 原凭证保留。
- 该笔不再计入报销总额。
- 历史仍保留。

### 部分退款
用户输入退款金额：

最终实报金额 = 原实付金额 - 退款金额

PDF 可显示：

原实付 ¥300.00 / 退款 ¥80.00 / 实报 ¥220.00

支持给该笔记录追加“退款凭证图片”。

PDF 中原支付凭证后紧跟退款凭证。

---

## 15. 主状态

第一版仅保留 5 个主状态：

1. 识别中
2. 待处理
3. 可报销
4. 已生成报销单
5. 已归档

退款作为属性，不增加主状态。

---

## 16. PDF 输出结构

一次结批最终生成一个完整 PDF，例如：

P1：报销单 001  
P2–P4：001 对应凭证

P5：报销单 002  
P6–P8：002 对应凭证

生成 PDF 前提供完整预览。

允许轻量手动调整：将某个分类移动到上一张/下一张报销单。

---

## 17. 页面结构

### 首页 / 上传凭证
- 大型拖拽区
- 单次最多 50 张
- 上传/识别进度
- 成功数
- 待处理数

### 本期报销池
- 当前可报销记录
- 分类统计
- 总金额
- 编辑、退款、删除、查看原图
- “生成报销单”入口

### 待处理
只展示异常：
- 金额无法确定
- 分类低置信度
- API 最终失败
- 疑似重复
- 其他无法自动放行情况

### 生成预览
- 系统自动拆好的报销单
- 报销部门
- 年/月/日
- 报销人模式
- 备注选择
- 轻量手动调整
- 生成 PDF

### 历史报销单
按月份查看：
- 报销批次
- 金额
- PDF
- 原始凭证
- 退款凭证
- 归档状态

### 设置
- 报销部门
- 日期设置
- 报销人姓名
- 报销人签名
- 备注信息库
- AI 学习记录
- API 配置状态
- 备份与存储管理

## 18. 本地存储

技术方案：
- 前端：React + Vite
- 本地后端：Node.js
- 数据库：SQLite
- AI：可替换的多模态 API
- PDF：本地 PDF 生成模块

SQLite 不直接保存大图片，只保存结构化信息和图片路径。

建议目录：

data/
  2026-09/
    originals/
    refunds/
    exports/

数据库保存：
- 凭证 ID
- 原图路径
- 上传顺序
- 识别金额
- 最终金额
- 分类
- 商家
- 日期
- 置信度
- 退款信息
- 状态
- 报销批次 ID
- 归档状态
- 图片指纹
- 学习规则
- 设置
- 备注库

原始凭证一旦上传，不由 AI 修改。

---

## 19. API Key 与 AI 服务解耦

API Key 只存本地后端环境配置，不写进 React 前端。

前端：
浏览器 → localhost Node 后端

后端：
Node → 多模态 API

统一 AI 接口建议：

analyzeReceipt(image)

系统内部只依赖标准输出：
- amount
- category
- merchant
- date
- confidence

以后可替换不同支持视觉理解的模型，而无需重写整个报销系统。

---

## 20. 归档与清理

默认长期保留全部数据。

### 归档
- 按月份归档。
- 仅从日常工作区隐藏。
- 不删除原图或结构化记录。

### 清理原图
- 用户主动触发。
- 二次确认。
- 删除原始图片后仍保留 PDF、金额、分类、日期、报销批次和历史结构化记录。

---

## 21. 备份

设置页提供“备份全部数据”。

第一版至少备份：
- SQLite 数据库
- 设置
- AI 学习规则
- 文件索引

后续版本可增加“导出本月档案 ZIP”。

---

## 22. 第一版成功标准

以真实门店报销图片测试。

理想流程：

打开网页  
→ 拖入几十张图片  
→ 后台自动识别  
→ 用户只处理少量异常  
→ 点击生成报销单  
→ 选择报销部门/日期/报销人/备注  
→ 预览  
→ 导出完整 PDF

核心验证指标：

1. 正常凭证自动识别率
2. 实付金额准确率
3. 分类准确率
4. 异常拦截率
5. 重复凭证拦截率
6. 从上传到最终 PDF 的总耗时
7. 相比原人工流程节省的时间
