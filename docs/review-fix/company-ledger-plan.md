# 公账付款区方案（和店内报销隔离的独立区域）

来源：2026-10-01 试点后新增需求。公司账户付出的款（肉款、品牌管理费、店面租金、物业费…）要有单独的区域，和店内报销隔离。
基于 f489d1e。做哪个 task 就只读本文件里该 task 列出的文件和测试。每个 task 单独提交，做完在文末「进度」打勾，并在 `progress.md` 记一段。

## 需求和已确认的选择（2026-10-01，全部按推荐）

输入是银行电子回单（转账给供应商）和收款方开的收费通知单，例如：

- 回单：付给上海新沣食品销售有限公司 12,909.49（肉款）；付给武汉市火门品牌管理有限公司 6,785.00（品牌管理费）。
- 收费通知单（武汉远洋里）：租金 22,814.10（2026 年 9 月）+ 物业费 5,069.80（2026 年 9 月）+ 水费 48.86（2026 年 7 月）+ 电费 11,466.87（2026 年 7 月）+ 空调能源费 162.00（2026 年 7 月）= 39,561.63。底部写着汇款的收款户名、银行名称、账号。

| 问题 | 选择 |
| --- | --- |
| 公账区产出什么 | 「公账付款单」PDF：和店内流程一样，汇总页按分类汇总，每张回单、通知单附在后面；单独编号、单独历史，和店内报销完全分开 |
| 收费通知单 | 一张图只存一份，AI 读出各收费项目（带期间），每项一行，人可以改（见下面「补充」：水费、电费、空调能源费分开，不合并） |
| 访问权限 | 先不限制，同一个访问码 |
| 店内已有的「肉类」「租金及管理费」 | 保留不动；公账区另有自己的分类，两边互不影响 |

### 补充（2026-10-01，用户看了通知单后）

1. **收款方信息写进付款单的「备注」栏**：收款户名（公司名称）、开户银行、银行账号。每张回单、通知单都读出收款方三项，编辑框里可以改；付款单一页上有几个收款方就列几个，字号自动缩小到放得下，实在放不下接到备注续页。这条取代最初的「不存银行账号」。
2. **水费、电费、空调能源费单独成项，不合并**，每一项带「费用月份」（通知单上的「期间」）：付款单上写成「电费（2026年7月）」「店面租金（2026年9月）」。同一个分类不同月份是两行，不加在一起。回单用途里写了月份的也读出来；读不出就不写，随时可以改。原因：这张通知单里是上个月的水电能源费和下个月的租金。

公账区的分类（八类）：肉款、品牌管理费、店面租金、物业费、水费、电费、空调能源费、其他公账支出。
最后一类是兜底：回单上写的是装修款、广告费这类不在前几类里的，也能记下来，不会被迫记错分类。不想要可以去掉。
（水电合写的「水电费」分不开水和电，不猜，落到「其他公账支出」并提示人拆开。）

## 不做的

- 不做单独的访问码或角色权限（以后卖给老板、总部和门店分账号时再做，见文末「以后」）。
- 不做回单和通知单的自动对账（比如通知单合计 39,561.63 对上银行回单）。
- 不做「识别出这是公账凭证却传到了店内」的自动检测。传错区的办法：在传错的区删除，再传到对的区（见「查重」）。
- 账号的使用范围很窄：只存在收款方（`payee.account`）这一个字段里，只在编辑框、对账页和付款单备注栏里出现；识别结果的依据、关键词、商户名里出现的账号一律抹掉（关键词会被学成规则，不能是账号），日志里不记。付款人的账号、联行号都不读。

## 数据模型（全部新增字段可选，老数据一律当店内处理，不需要迁移）

- `Ledger = 'store' | 'company'`。`Receipt.ledger?`、`Batch.ledger?`：缺省就是店内。店内的凭证和批次存下来的数据和现在完全一样。
- 分类：`CATEGORIES`（店内十类）不变；新增 `COMPANY_CATEGORIES`（公账八类）；`Category` 是两者的并集。
  - `categoriesFor(ledger)`、`categoryLedger(category)`、`ledgerOf(row)`。
  - 规则（`Rule`）属于哪个区由它的分类决定，不再加字段。
- 费用月份：`period`，格式 `YYYY-MM`。`isPeriod`、`parsePeriod`（认「2026年7月」「2026-7」「2026/07」等写法）、`formatPeriod`（2026-07 → 2026年7月）。
- 收款方：`Payee = { name?, bank?, account? }`（户名、开户银行、账号）。
- `Receipt.lines?: ReceiptLine[]`（`{ category, fen, period? }`）：一张凭证拆成多项。只在公账区出现，至少 2 项（不同的「分类 + 月份」至少 2 种）、「分类 + 月份」不重复、每项大于 0；确认后 `paidFen` 等于各项之和。`Receipt.category` 取第一项，只作为兼容字段。
- `Receipt.period?`：单分类的公账凭证的月份（有 `lines` 时月份在各项里）。`Receipt.payee?`：收款方。
- `Snapshot.lines?`、`Snapshot.period?`、`Snapshot.payee?`：批次里的凭证快照带同样的内容，定稿后不再变。
- `FormGroup.period?`：付款单上的一行是一个「分类 + 月份」，同分类不同月份是两行。
- `Analysis.lines?: Array<{ label, amount, period? }>`：AI 读到的原始明细（费用项目原文 + 金额 + 期间），留作依据。服务器再把它们映射成分类。`Analysis.period?`、`Analysis.payee?`：AI 读到的月份和收款方。
- `Settings.companyDepartment?`：付款单上「付款单位」的默认值（公司名）。

## 隔离清单（每一项都按区域过滤，不带区域参数的请求等于店内）

| 位置 | 做法 |
| --- | --- |
| 上传 | `POST /api/receipts/upload?ledger=company`（multer 不允许带表单字段，所以用查询参数）；凭证记下 `ledger` |
| 列表、汇总 | `GET /api/receipts?view=…&ledger=`、`GET /api/pool/totals?ledger=`；汇总只列本区的分类，明细凭证按各项分到各分类 |
| 识别 | 队列把凭证的区域交给 AI：公账用公账提示词和公账校验；`decide()` 只看本区的规则 |
| 规则 | `GET /api/rules?ledger=`、`POST /api/rules/reapply?ledger=`；学习规则的 id 公账区加 `company:` 前缀，免得和店内同名特征互相覆盖 |
| 查重 | 完全一样的图：另一区有「在用」的同一张也拒绝（防重复入账），回收站里的另一区同一张不算（传错区后可以重传）；从回收站恢复、拆开合并凭证时，另一区已有同一张在用的，拦下（`LEDGER_DUPLICATE`）；疑似重复（相似图）只在本区比；公账区不在上传时做相似图判断（见风险） |
| 合并截图 | 只能合并同一区的；合并出来的凭证继承区域 |
| 批次 | 一个批次只能是一个区的凭证（混了返回 409）；`Batch.ledger` 记下来 |
| 历史、归档、清理 | `GET /api/history?ledger=`、`POST /api/archive/:month?ledger=` 等；某月的归档、取消归档、清理原图只动本区 |
| 退款 | 公账区不支持退款（银行转账没有这个概念），接口直接拒绝，免得和明细对不上 |
| 备份 | 照旧，全部数据一起备份（含收款方信息） |

## 一张凭证多项明细（收费通知单）

- AI 返回 `lines`（费用项目原文 + 金额 + 期间）、整张的合计 `amount`、收款方 `payee`。服务器按关键词把每项映射到分类，**同分类同月份**的合并：
  - 含「品牌、加盟、特许」→ 品牌管理费；「租金、房租」→ 店面租金；「物业、物管、管理费」→ 物业费；「空调、能源、能耗」→ 空调能源费；「电费、电力、用电」→ 电费；「水费、用水、自来水」→ 水费；「水电」（合写）和其余 → 其他公账支出（要人看一眼）。顺序有讲究：品牌在管理费前，空调在电费前。
  - 例子里的 5 个项目各是一行：租金（2026-09）、物业费（2026-09）、水费（2026-07）、电费（2026-07）、空调能源费（2026-07）。
- 只有一项且认得出分类的通知单，当单分类凭证（用这一项的分类和月份）；只有一项而且认不出的（多半是回单上多写了一行），按 AI 给的单个分类处理，明细只留作依据。
- 校验：各项之和必须等于合计（否则原因 `lines_mismatch`「各项金额加起来和合计对不上」）；有项目落到「其他公账支出」（认不出的项目）也要人看一眼（`category_uncertain`）。进待处理，原因写清楚，编辑框里直接改。分类由收费项目映射，不看规则，也不看 AI 给的分类置信度。
- 编辑：有明细的凭证，编辑框显示每项「分类 + 月份 + 金额」，可增删，下面实时显示合计；没有明细的公账凭证可以点「拆成多项」手动拆。AI 没读出明细时，人工也能拆。
- 排版：付款单上的一行是一个「分类 + 月份」；同一张凭证出现在几行里。附件页只附一次（同一张付款单页内去重），页眉写「本张凭证含 5 项：租金（2026年9月）…」。
- 对账页清单里，这张凭证在各行下各有一个金额，点哪个都是同一张图。

## 公账付款单（PDF）

沿用店内报销单的版式（5 行、金额栏、大写、备注、签字），换成公账的叫法：

| 位置 | 店内 | 公账 |
| --- | --- | --- |
| 标题 | 费用报销单 | 公账付款单 |
| 左上 | 报销部门： | 付款单位： |
| 表头 | 报销项目 | 付款项目 |
| 项目栏 | 分类名 | 分类名 + 月份，如「电费（2026年7月）」 |
| 备注栏 | 备注模板 | 本页各张凭证的收款方（收款户名、开户银行、银行账号），去掉重复的；选了备注模板的话接在后面 |
| 页脚 | 报销人 | 经办人 |
| 附件页页眉 | 第 N 张报销单 · … | 第 N 张付款单 · … |

付款单位默认取设置里的「公账：付款单位」；日期、签名方式、备注模板和店内共用。备注栏里收款方多、放不下时字号从 10pt 逐级缩到 6.5pt，再放不下才接到备注续页。

## 风险和应对

- **真实 AI 对银行回单、收费通知单的识别没有实测过。** 提示词写得很具体（回单读哪几个字段、通知单怎么列明细和期间），服务器再做二次校验（明细之和等于合计），编辑框能手动改，设置里能加固定规则。第一次用真实图片跑，需要的话再调提示词。
- **银行账号是十几位数字，AI 读错一位就是错账号。** 提示词要求看不清就填空、不要猜；对账页把收款方放在凭证图旁边，付款前对着原图核对；编辑框能改。付款单上的账号来自这里，所以这一步不能省。
- **银行回单模板完全一样，相似图判断会把不同的回单误当重复。** 公账区不在上传时做相似图判断；识别之后仍按「同金额、同日期、同收款方、图相似」判断，和店内的二次判断一样。
- **`Category` 变成两个区的并集。** 凡是用「在 `CATEGORIES` 里」校验的地方（上传后的修改、确认、移动分类、规则）都要改成按区域校验，类型检查会把漏的找出来。
- **老数据。** 没有 `ledger` 的当店内，没有 `lines`、`period`、`payee` 的当单分类，店内批次的 JSON 和以前一样。可以随时回滚到 f489d1e，不会留下读不了的数据（新字段都是可选的，旧代码会忽略它们）。
- **一张付款单页上收款方多。** 备注栏只有 5 行左右的地方，3 个收款方要缩到 7pt 才放得下，更多的接到备注续页；用户想让一页只放一个收款方的话，以后可以在排版时按收款方分页。

## 以后（这次不做）

- 单独的访问码或角色：多店版本里，总部账号看全部，门店账号只看自己店的店内区，公账区只有总部能进。
- 回单和通知单自动对账；公账凭证传错区的自动提示；「移到另一个区」按钮。
- 收费项目名称保留原文（现在不在八类里的项目统一显示「其他公账支出」，分类名替代了项目名）；自定义公账分类。
- 排版时让同一张通知单的各项尽量排在同一页；按收款方分页。
