# 自动报销系统修复 Implementation Plan

> 执行方式：由 Kimi 在现有项目内顺序执行，每次一个 Task。若已安装 superpowers，使用 executing-plans；本轮不启用并行 Agent，不为每个 Task 另开一个全库审查。用户已要求制定并执行这些修复，不重复索取日常修改确认。

**Goal：** 修复模板、分类、备注、报销人/部门持久化和同屏对账五个问题，以实际生成文件和手机操作验收。

**Architecture：** 沿用现有技术栈、存储和导出方式；把报销批次数据作为预览与导出的共同来源。屏幕对账使用双分区，导出继续使用纸张分页。

**Tech Stack：** 本文未读取项目仓库，技术栈、文件路径、根因均不作虚构。Task 00 必须在当前仓库查证并固定路径和执行命令，后续 Task 使用这份索引。

**Spec：** 以本文“需求与边界”、用户提供的两张问题截图、`费用报销单_矢量复刻.svg`、`费用报销单_高清复刻.png`、`费用报销单_清晰复刻.pdf` 为准。SVG 是模板几何基准，PNG/PDF 用于视觉比对。

## 需求与边界

1. 用最新清晰复刻版替换现有报销单模板，保留蓝绿色楷体文字、黑色细线、5 行明细、金额位格、右侧备注/领导审批、底部金额大写和签名区域。
2. “百慕达食材”和“食材”必须是两个独立类别，识别、保存、恢复、汇总、预览、导出全链路保持区分。
3. 备注有可打开的多行输入窗口，支持保存、取消、清空；保存内容进入本张报销单备注区域。
4. 报销人、报销部门从输入到保存、刷新恢复、生成预览及下载文件都保持一致。“不能稳定上传报销单”可能涉及字段丢失或真实上传失败，必须实际复现，不只改显示文案。
5. 查看凭证时仍能看到报销单，支持选中明细与相应凭证的关联查看，手机同样可用。

## Global Constraints

- 修复现有项目，不重建整个系统、不更换框架、数据库、AI 提供商或部署平台，不升级无关依赖。
- 优先复用现有 API、状态管理、存储和测试设施。确需字段变更时做向后兼容，旧数据缺少新字段仍能打开，不清库、不删除历史报销及凭证。
- 不修改无关登录、权限、去重、撤销和学习系统；若其中某条规则直接导致本轮问题，只修正已定位的路径。
- 每笔金额使用总实付金额；金额运算沿用可靠的十进制或整数分实现，禁止通过显示四舍五入掩盖汇总误差。
- 上传顺序稳定；不得因异步识别完成时间、分类调整、重新渲染而打乱凭证顺序。沿用已有分类汇总规则，但每个汇总行必须能追溯到真实凭证 ID。
- 允许为屏幕加入按钮、选中态和对账信息，导出/打印的空白表格结构必须与提供模板一致。
- 模板当前画布为 210 × 117.9 mm，是照片比例重绘；没有实物尺寸信息，不宣称已校准原纸张尺寸。保留原图比例，若项目输出 A4，将模板等比放到现有纸张上，禁止拉伸或更改整套导出纸型。
- 正常开发在本地/预览环境完成。本计划不包含自动发布线上版本或操作真实报销数据。
- 不在日志、截图、报告中泄露凭证里的完整手机号、地址、密钥等信息；测试使用匿名样本。

## 降低反复读代码的执行协议

1. Task 00 做一次定向定位：先看 AGENTS.md、目录、依赖/脚本和工作区状态，再用 rg 查找五个问题的入口，不输出整仓源码。
2. 创建 `docs/reimbursement-fix/context-map.md`，按 Task 记录真实文件路径、关键符号、调用关系、现有测试、具体测试命令、重要决策。索引里记录“为什么读这个文件”。
3. 创建 `docs/reimbursement-fix/progress.md`，每个 Task 只记录状态、改动文件、原因、验证结果、剩余问题。接口变动及时更新 context-map；索引是导航，不代替当前源码。
4. 每次开始只读本 Task、进度摘要、对应源码及直接依赖。需要越界时说明具体调用关系后再读，禁止因为切换 Task 就重扫全库。
5. 一个 Task 失败，只修本 Task 及直接受影响路径，不重做已通过任务。具体证据证明前序任务有问题时，才重新打开对应项。
6. 每项先复现问题，再做最小修复；有业务数据风险的分类、持久化、汇总需要有针对性的自动测试，纯样式以渲染比对和操作验收为主。
7. 同一会话顺序推进；上下文不足才换会话，新会话读取计划、进度、相关文件。不要为了节省读取而跳过必要依赖，也不要不断输出完整大文件消耗额度。
8. 每 Task 形成独立差异/提交；已有 Git 仓库时仅提交自己修改且已验证的文件，不包含用户未提交的改动，不自动推送。
9. 每 Task 报告：改了什么、为什么、如何定位、以后如何查、验证证据、下一 Task。不把“代码已修改”当作“验收已通过”。
10. 能直接编辑仓库就交付完整实际文件；需要用户手动替换时，提供修改文件的完整内容，不只给零散补丁。

## Review Focus

- 旧数据缺少字段、刷新和批次切换：不得丢输入或把 A 批次数据写到 B 批次（Task 01、03）。
- 用户修改和 AI/历史规则冲突：人工分类不能被迟到结果覆盖（Task 02）。
- 输入后立即生成、连续生成、旧请求后返回：下载必须对应最新已保存数据（Task 01、04）。
- 超过 5 个分类、长备注、长部门名：不得裁切、漏项、静默截断（Task 03、04）。
- iPhone 地址栏、横竖屏、软键盘和长截图：同屏查看成立，编辑/关闭/切换仍可操作（Task 05、06）。

## Task 00：一次性定位，固定后续读取范围

**Files：** 只查真实入口；新增上述 context-map.md、progress.md。不要先假定项目是 React 或后端使用某种数据库。

**输入：** 当前仓库、现有运行方式、本文、参考文件与两张截图。
**输出：** 每个 Task 的真实文件/关键符号/可执行测试命令；生成链路及数据流图可用短文字记录。

- [ ] 查 AGENTS.md、工作区未提交改动、启动/构建/测试脚本，沿用项目约定。
- [ ] 定位上传与 OCR/AI、分类归一化、学习/历史规则、批次保存与读取、表单字段、备注、预览、PDF/打印、附件列表入口。
- [ ] 分别记录五个问题的最短复现步骤；能观察到的症状与尚未证实的根因分开写。禁止把截图看不到输入框直接当成 API 丢字段的证据。
- [ ] 给 Task 01–06 填写真实修改/测试文件路径和现有函数签名；只为确需新建的功能定义新符号，不创建平行重复数据层。
- [ ] 记录报销数据如何关联凭证、是否按分类汇总、报销人与部门来自哪里、当前预览是否使用 PDF iframe/原生阅读器。
- [ ] 将参考模板放进项目现有资源目录，记录准确路径；不得拿问题截图里的旧模板当基准。

**通过条件：** 不改业务代码也能指出每个问题的调查入口和验证方法。确有运行环境阻塞时记录错误，只暂停受阻任务，不反复重读代码。

## Task 01：报销人、报销部门稳定保存并进入报销单

**Files：** Task 00 索引中的报销基本信息表单、批次保存/读取接口、字段校验、存储映射、生成参数、对应测试。
**输入：** 当前批次 ID、用户输入、已有保存方式。
**输出：** 当前批次的可靠数据快照；至少包含报销人、部门、日期、备注、条目及凭证关联。沿用现有真实字段名，统一读写映射。

- [ ] 先复现：输入报销人“测试报销人甲”、部门“武汉测试店”，保存后检查请求、响应、存储/读取结果，再生成和下载，定位丢失发生在哪一步。
- [ ] 排查字段命名不一致、默认值覆盖、组件卸载重置、异步回写旧值、仅存内存、生成请求漏传、上传接口拒绝等实际路径，仅修有证据的问题。
- [ ] 保存成功必须有明确状态；保存失败保留输入并给出可重试提示。生成若依赖保存，等待保存成功后再取同一快照，避免点击过快读到旧值。
- [ ] 防止旧保存/生成响应覆盖新输入，复用现有请求序号、版本或取消机制；不要为这点另建复杂并发系统。
- [ ] 本批次数据与可选“下次默认值”分开。编辑默认值不能回写历史单据，批次切换不能串值。
- [ ] 回归：保存后刷新、重新打开、A/B 批次切换、修改后立即生成、失败后重试、两次快速生成；页面、请求、恢复数据、下载文件均一致。

**通过条件：** 上述路径稳定通过。若实际存在图片上传失败，也必须有独立复现与修复证据，不能只靠字段显示就关闭问题。

## Task 02：百慕达食材始终是独立分类

**Files：** 索引中的分类枚举/ID、AI 结构化输出解析、归一化规则、商家/历史规则、分类选择器、汇总与导出映射、相关测试。
**输入：** 识别建议、显式类别、用户选择、已存在且可信的规则。
**输出：** 全链路稳定类别 ID 及显示名；保留人工修改的事实，AI 只能提供建议。

- [ ] 用最小样本追踪“百慕达食材”从识别到导出的类别值，找出第一个变成“食材”的位置。优先检查子串匹配、包含“食材”的兜底、枚举缺项、ID 重用、旧学习记录。
- [ ] 保持两个独立类别 ID；禁止两者共用 ID 后只改显示文本。优先级：人工选择 > 明确完整类别/已确认的精确规则 > AI 建议 > 待确认。人工结果不得被后台重新识别覆盖。
- [ ] 精确完整匹配先于模糊/通用匹配；空格可规范化，但不得把“百慕达食材”裁成“食材”。若凭证本身无法区分，保留人工选择入口，不凭空推断商家与类别关系。
- [ ] 现有“学习”若覆盖人工选择，仅修该覆盖逻辑；不能顺带重写学习系统。历史“食材”记录无法证明属于百慕达时，不批量改写。
- [ ] 针对性测试：明确百慕达→百慕达；普通食材→食材；人工改为百慕达后重识别/刷新仍是百慕达；两类同时存在时不合并。
- [ ] 样本：百慕达食材 100.00 元、食材 50.00 元，分别显示两行/两个分类，总计 150.00 元；保存、重开、预览、PDF 均相同。

**通过条件：** 修到首次错误转换点，且证明后续各层保持分类，而非仅修改 AI 提示词或页面标签。

## Task 03：备注编辑窗口及批次保存

**Files：** 索引中的报销编辑表单/操作栏、现有模态框或抽屉、批次字段与保存测试。
**输入：** Task 01 当前批次快照。
**输出：** 已保存的本张报销单备注；Task 04 负责将其排入纸张。

- [ ] 在编辑/预览操作栏提供“编辑备注”按钮；屏幕自有表格的备注区可同时作为入口，但不能只有点击 PDF 文字这一种入口。
- [ ] 使用多行文本框，打开时读取已保存值；有“保存”“取消”。取消不修改，保存空字符串明确代表清空，不能误还原旧值。
- [ ] 保存后更新当前批次预览；保存失败保留输入并提示。中文输入法组合输入正常，手机键盘打开时按钮仍可到达。
- [ ] 支持中文、标点与换行；有既有长度限制则沿用并明确提示，无限制则不随意截断。纸上装不下的内容交 Task 04 处理。
- [ ] 若项目已有备注模板，保留入口，明确选择模板是替换还是追加；用户正在编辑的内容不能被后台模板自动覆盖。
- [ ] 测试多行保存、取消、清空、刷新恢复、A/B 批次互不影响；文本以纯文本呈现，不执行用户输入的 HTML。

**通过条件：** 用户能找到入口，保存与恢复一致；空备注、长备注、失败重试都可操作。

## Task 04：用新模板生成一致的预览与导出

**Files：** 索引中的报销模板、渲染/导出代码、字体资源、分页和金额格式函数、相应测试。
**输入：** Task 01–03 的批次快照及参考 SVG/PNG/PDF。
**输出：** 新模板报销页、可供对账页使用的同源数据和凭证关联。

- [ ] 以参考 SVG 的线框坐标和区域比例为基准；参考 SVG 文字已转曲线，不依赖系统安装同名字体。可复用为静态底版，在留白区填动态字段；也可复刻成现有模板组件，但不能凭肉眼另设计一份。
- [ ] 保留 5 行明细、9 个金额位格（百、十、万、千、百、十、元、角、分）、备注、领导审批、合计、金额大写、原借款、应退/补款、底部署名的位置。
- [ ] 动态值进入对应空白区域。金额以分为单位拆位，0.05、12.30、100.00 等小数位置正确；大写转换与总额一致，不溢出最大位数，超范围给出明确错误。
- [ ] 报销人、部门、日期、备注来自同一快照。预览/导出复用同一个布局来源；若导出仍走不同后端，使用相同布局参数并增加一致性对照。
- [ ] 超过 5 个汇总明细行按 5 行分页；每张只汇总本张实际行，另在屏幕展示整个批次总计。每张关联凭证清楚，禁止漏项、重复求和或为了塞下所有分类把原模板改成更多行。
- [ ] 长部门/姓名在自己的留白区换行或适度缩字号，不压过标签和表格；备注自动换行且不能盖住领导审批。备注超出原框容量时生成“备注续页”，原备注区明确提示续页，全文保留。
- [ ] 页数按现有业务定义核对，并从实际生成结果计算；如果字段“单据及附件共”原意包含报销页及附件页，就包含相关续页。禁止硬编码上传图片数量，因为一张长图可能分页。
- [ ] 使用截图的匿名金额样本：277.20、114.64、133.79，总计 525.63；如沿用分类汇总，能耗费 277.20、耗材 248.43，并保留耗材行的两个凭证关联。
- [ ] 渲染空白版与参考图等比叠加/并排比较，检查列线、行高、标题和各标签；再检查填写版、下载 PDF 及打印预览无错字、方框、裁切和重叠。

**通过条件：** 模板形状和区域与参考相符，金额与字段准确。对比证据来自实际导出文件，不只来自页面截图。

## Task 05：电脑和平板双栏对账

**Files：** 索引中的预览路由/组件、附件查看器、选中状态、必要的展示层样式。
**输入：** 同源报销快照、稳定的报销行 ID / 凭证 ID 关联、原始上传顺序。
**输出：** 同屏查看的对账工作区；关联状态供 Task 06 复用。

- [ ] 屏幕宽度 ≥ 900 CSS px 时采用左右双栏：左侧报销单，右侧附件。区域占用可用视口，各自滚动，右侧长图滚动不能把左侧报销单卷走。
- [ ] 复用现有附件/图片渲染能力；若现有 PDF 原生阅读器不支持此交互，在应用页面内增加对账视图，保留 PDF 下载入口，不尝试往原生 PDF 查看器注入输入框或布局。
- [ ] 右侧支持上一张、下一张、序号/总张数、缩放和恢复适宽；图片完整展示，不裁切原图、不强制压缩到看不清数字。
- [ ] 点击左侧分类行，定位该行第一张凭证；一行多个凭证时显示关联列表/数量，允许逐张看。手动切换附件时高亮所属行，保持原上传顺序。
- [ ] 附件标题显示序号、分类、该笔总实付金额；汇总行合计与单笔金额区分。不可只靠数组下标做关联，防止排序、删除后错配。
- [ ] 验证 1440×900、1024×768：浏览长凭证时左侧仍可见；空附件有明确空状态，图片加载失败可重试且不丢当前报销单。
